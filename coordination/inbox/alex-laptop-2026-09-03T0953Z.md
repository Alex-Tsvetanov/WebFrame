# HTTP/3: first execution, endpoint verified, and a schema field that was wrong rather than missing

## The tests ran, and they pass

11 test cases, 3916 assertions, all passed, 9 ms. Nothing skipped: 11 `TEST_CASE`s exist
across the four `test_http3_*.cpp` files and 11 ran. This is the first execution of that
code path anywhere in the project.

## The build system hides them, and this is the more important finding

Each of those four files wraps its entire body in `#ifdef COROUTE_HAS_HTTP3`. Without the
define the tests do not skip — they do not exist. The file compiles to nothing.

- ordinary builds: **175** test cases listed
- HTTP/3 build: **187** listed (11 HTTP/3, plus one unrelated newer test)
- an ordinary build asked for `[http3]` answers **"No tests ran"** and exits 0

So every green run this suite has ever had was green while containing eleven fewer tests
than the source defines, and nothing in the output said so. A skip at least prints. This is
the same disease as rule 4a: *no tests ran* and *no tests exist* produce the same output,
and only one of them is a pass. The suite should refuse a build whose case count is below
what the sources define, or at least print the count.

## The endpoint comes up

Self-signed cert in a scratch directory; server with TLS and HTTP/3 on, 2 workers, io_uring.
The banner claims `HTTP/3 listening on UDP ... across 2 worker(s)`, but that claim is the
thing under test, so it was checked against the kernel instead: **two UDP sockets bound,
one per worker under SO_REUSEPORT**, confirmed both in `ss -ulnp` and in `/proc/net/udp` by
socket inode, with the two TCP listeners alongside. Clean shutdown on SIGTERM in 1.6 ms.

Compiling is not serving; here it serves, to the extent that the socket exists and is
bound. No handshake has been attempted. Note for whoever writes the next step:
`tests/integration/verify_http3.sh` already exists and drives this endpoint with ngtcp2's
reference client, as does `verify_multiprotocol.sh`. Neither has been run.

## Schema 10: the QUIC versions were populated and wrong

`dependency_versions` already carried `ngtcp2` and `nghttp3`, under the correct pkg-config
names. The field was not missing. It was wrong in three ways, which is worse, because a
populated field gets quoted:

1. **It asked the host's package database, not the artefact.** HTTP/1.1, TLS-off records
   on this machine carry `ngtcp2 1.25.0` for a binary that links no ngtcp2 at all.
2. **It was read when the harness ran, not when the server was built.** A campaign
   spanning a routine package upgrade would record the new version against a server built
   against the old one — precisely the failure the field exists to detect, concealed
   behind a plausible number.
3. **Absent could not be told from unrecorded**, so a missing key meant either "no QUIC"
   or "predates the field".

Fixed on `linux/quic-linked-versions` (`ef65ff6b4`, off `phase0-foundation`). The soname is
resolved against the server binary the run launches: `<name>_lib` is the file it resolves
to and cannot be wrong; `<name>` is pkg-config's release version, recorded only when
pkg-config's libdir describes that same file. Absent when the binary links no QUIC.
Verified against both builds. Harness selfcheck: 336 checks pass.

**Consequence for anyone reading existing records:** the QUIC versions in every record at
schema 9 or below describe the machine, not the run, and must not be quoted as the
apparatus of those campaigns.
