### What this says

Shape dominates backend. Churn costs about 4.5x the syscalls per request of keep-alive
on both backends, while the two backends differ from each other by under 4% within a
shape. If that survives a controlled machine it is the socket-demux paper's mechanism
result, and it says the interesting axis is connection lifetime rather than which Linux
backend is compiled in.

The arms are mechanically distinct and the tracepoints prove it rather than assuming it.
The io_uring cells show zero epoll_wait, zero recvfrom, zero sendto and zero accept4:
that work is inside the ring. The epoll cells show zero io_uring_enter. Nobody has to
take the banner's word for which arm ran.

io_uring_enter at 4.75 per request in keep-alive is worth someone's attention. If the
ring were batching well it should be far below one. It suggests one enter per operation
rather than per batch, which is a finding about this implementation and not about
io_uring, and it is exactly the kind of thing the portability paper should be able to
state with a number.

### Instrument choice: perf yes, strace no

The audit's prediction is confirmed, decisively. Cell 1's shape re-run under
`strace -c -f` instead of perf:

  under perf    200000 completed, 20000 rps
  under strace   36233 completed,  3623 rps    18.1% of the perf run

strace costs 82% of throughput. It cannot be used for a timed run. perf's own cost is
not separately measured here, but a run under perf achieved the full offered 20000 rps,
so whatever it costs it did not bind at this rate.

strace does earn its place as a discovery tool, though, because `strace -c` names the
syscalls my tracepoint list missed:

  sendto        36297      clock_gettime  73204   (~2.0/req)
  epoll_ctl     72886      recvfrom       36361
  futex           382      epoll_wait      1178

clock_gettime at about 2 per request and epoll_ctl at about 2 per request are most of
the unnamed 61.5% in cell 1. If you want the named tracepoints to account for the total,
add those two. Better still, now that bpftrace is installed, a single
`bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[args->id] = count(); }'` gives the
whole histogram by syscall number with no list to maintain and no guessing.

### Caveat that limits cells 2 and 4

Both churn cells achieved about half the offered rate: 10512 and 11005 against 20000
asked for. They are throughput-limited, not open-loop, so the syscalls-per-request
number is sound but the rate is not a controlled variable between the keep-alive and
churn rows. loadgen returned rc=3 on cell 4, which is its own admissibility verdict
about the achieved share, and it was right to. For a real measurement the churn cells
need either a lower offered rate or an acknowledged closed loop.

Second caveat: the perf window is 13 s against loadgen's 10 s, so a few seconds of idle
server are inside every count. An idle server blocks rather than spins, so the error is
small, but it is not zero and it inflates syscalls/request slightly and unevenly.

                       \___ can't access trace events

harness feature built on this has to assume root or a relaxed tracefs.

## Two corrections to what I told you earlier

1. "This laptop cannot run io_uring" was wrong. kernel.io_uring_disabled=1 means
   restricted to CAP_SYS_ADMIN, not off. Alex caught it. The skip behaviour we built is
   still correct for the unprivileged case and every skip you have seen is right, but
   the backend is testable here under sudo and I have now tested it.

2. My first attempt at cells 3 and 4 produced zero syscalls and I nearly reported it.
   `pgrep -f | head -1` returned the sudo wrapper rather than the server, and perf
   counted a process sitting in wait(), which perf reports as `<not counted>` rather
   than as an error. The obvious fix, matching /proc/PID/comm against
   "benchmark_server", also silently failed: TASK_COMM_LEN truncates comm to 15
   characters, so it reads "benchmark_serve". Both failure modes are quiet and produce
   a plausible-looking file. Anyone building the perf counter into the harness should
   assert that raw_syscalls is non-zero before believing a cell, because both of these
   fail toward a confident wrong answer rather than toward an error.
