# alex-laptop: churn ladder, per-core clocks, and the backend mechanism

Three results. The churn ladder settles both open questions and they come out opposite
ways. The per-core clocks show io_uring holds the package about 147 MHz down, and the
offset is flat in load rather than monotone. And the mechanism is found, at a named line.

## 1. Churn ladder, io_uring, three rates, each delivering its offered rate exactly

    rate  reqs   clock_gettime  /req   /sec  |  uring_enter    /req     /sec   accepted
     100  2500          21475  8.590    859  |     5738047  2295.2  229522   no
     200  5000          42571  8.514   1703  |     5716351  1143.3  228654   no
     500 12500         108028  8.642   4321  |     5813615   465.1  232545   yes

Least squares on count/sec = a*rate + b:

    clock_gettime :  a = 8.6720 /req,  b =    -18 /s   residuals +1.2%, -0.8%, +0.1%
    io_uring_enter:  a = 8.8057 /req,  b = 227892 /s   residuals +0.3%, -0.4%, +0.1%

**clock_gettime under churn is purely per connection.** The floor is minus eighteen a
second, which is zero, and the per-request figure is flat across a fivefold rate change.
So about 8.7 clock reads per established connection is real work, against 2.00 per
request on an established one, and the deadline machinery arming more than once per
connection is the live hypothesis with nothing arguing against it. That is where this
started, before my bad two-point fit talked everyone out of it.

**io_uring_enter is the mirror image**: a floor of 227892 a second plus about 8.8 per
connection of genuine work. The floor matches the keep-alive measurements of 236123 and
227547 a second, so the poll loop is now measured at about 230000 a second across two
connection shapes and five rates. The small per-request component is visible for the
first time here, because at these rates the floor no longer swamps it.

## 2. Per-core clocks: the offset is flat in load, not monotone

Same method as before, both arms over the pair, all sixteen cores read from
/proc/cpuinfo every 0.5 s, both arms delivering identical completed counts.

    fastest core, io_uring minus epoll
      idle, server up, no load      -147 MHz
      3000 requests a second        -152 MHz
      10000 requests a second       -141 MHz

Three points from zero to ten thousand and the gap does not move. That is a stronger
answer than monotonicity would have been: a gap that is the same with no requests as
with ten thousand a second is not caused by the requests. It is caused by the thing the
backend does regardless of them.

At 3000 the per-core medians are mostly between -180 and -216 MHz with a median of
-181. Three of sixteen cores came out positive, +244, +90 and +238. I have not chased
those; with the generator, the sampler and four workers all moving between cores, three
outliers in a single thirty second run is not something I would read as structure, and
the fastest-core figure and the median are both stable across the two rates.

## 3. The mechanism, read and not changed

`src/net/io_uring/uring_context.cpp`:

    line 473   worker_loop:  while (!stopped_) { poll_and_resume(i); process_callbacks(i); }
    line 489   comment:      "Use short timeout - balance between latency and CPU usage"
    line 492   ts.tv_nsec = 1000;   // 1us timeout for low latency
    line 506   io_uring_wait_cqe_timeout(&worker_ring->ring, &cqe, &ts)

The loop is unconditional and nothing blocks it. Each turn issues one io_uring_enter
with IORING_ENTER_GETEVENTS and a one microsecond deadline, so with nothing to do the
wait returns immediately and the loop turns as fast as the syscall allows. Four workers
at about 58000 turns a second each is the 230000 measured. The rate is set by how long
an enter takes on this host, not by the workload, which is the time-proportional
signature exactly.

**A correction to the code's own comment while I was there.** Line 145 says
io_uring_wait_cqe_timeout takes an SQE for its timeout on kernels without
IORING_FEAT_EXT_ARG. This kernel has it: I read the feature bits from a live ring,
features=0x3ffff with IORING_FEAT_EXT_ARG set. So liburing uses the extended-argument
path and no timeout SQE is consumed here. The sq_mutex is still needed for other
reasons, but not that one. The comment is not wrong in general; it does not describe
this host.

### The smallest change that would test it, not made

Raise `ts.tv_nsec` at line 492 from 1000 to about 1000000, one millisecond. One line, no
structural change. If the diagnosis is right the enter floor should fall roughly in
proportion until it meets the real completion rate, the per-core offset should shrink or
vanish, and the cost should reappear as latency on the first request after an idle gap.

That last is the trade the comment at line 489 is deliberately making, so this is a
choice about the trade rather than a bug fix, and it wants measuring both ways. The
better change is probably not a larger constant but blocking when nothing is in flight
and spinning only when something is; that is structural and should be designed after the
one-line version has shown the size of the effect. Either belongs on its own branch with
before and after measured identically, and the before is only trustworthy because
nothing has been touched.

## Mediator, not confounder

Accepted, and it is the better reading. The treatment causes the clock change, so the
slower package is part of what io_uring costs rather than something to adjust away, and
adjusting for it would delete part of the effect. The clock goes alongside the latency,
not into it. Limitation to state with it: the magnitude is hardware-specific, since a
part with no boost headroom or a fixed-frequency server part would show little of this,
so the claim is that the mechanism exists and this is its size on this class of hardware.
