## Headline: the RESOURCE_LOCK fix is refuted. Nothing was pushed.

The instruction was a ctest `RESOURCE_LOCK` on the io_uring test registrations, one
property, no code change, confirm 184/184. I built exactly that. It does not fix the
failures, and establishing why overturned the diagnosis behind it.

In order:

1. Lock on the io_uring **unit** registrations only — still 2 failures, and a *different*
   pair than before. One was `tls_demux_io_uring`, an integration arm outside the lock.
2. That implies the budget is shared across processes. Probed directly, by creating
   8192-entry rings until ENOMEM: one process alone gets **9**. A second process started
   while the first holds **5** gets exactly **4**. 5 + 4 = 9, so **`RLIMIT_MEMLOCK` for
   io_uring is charged per-user, not per-process**, despite what the limit's name
   suggests. This finding stands independently of everything below.
3. Extended the same lock to `protocol_demux_io_uring` and `tls_demux_io_uring`.
   Result: 184/184.
4. **Repeated five times: 100%, 99%, 100%, 99%, 99%.** The green run was luck. Reporting
   after the single run would have been a false confirmation.
5. Ran only the 7 locked io_uring tests at **`-j1`** — no concurrency whatsoever — five
   times: **2 of 7 fail, every time.**

Step 5 kills the hypothesis. The failure never required parallelism, so serialising
execution cannot address it.

### Actual cause

The per-user budget is released **asynchronously**, 7–14 ms after the holding process
exits (measured, three trials each: 12.5 / 13.7 / 12.5 ms to recover all 9 rings;
8.0 / 12.3 / 6.9 ms to recover the 4 a worker context needs). ctest starts the next test
far faster than that. Consecutive io_uring tests therefore **overlap in accounting while
never overlapping in time**. Each failing test passes 100% of the time when run alone.

Falsifiable prediction, tested — the 4 io_uring cases back to back, 3 reps, varying only
the gap between them:

```
  gap   0 ms  ->  8 failures / 12
  gap  50 ms  ->  1 failure  / 12
  gap 200 ms  ->  0 failures / 12
```

A delay fixes it; a lock does not. `RESOURCE_LOCK` is the wrong instrument for this
defect. Branch `linux/uring-test-resource-lock` reverted to clean, nothing pushed.

Three possible fixes, all above my remit and left to the coordinator: retry-with-backoff
on ENOMEM in ring init (a code change, and arguably correct for a production server too,
which can hit this on a real host); a smaller ring for tests (changes what is measured);
a larger ulimit (administrative, and hides the constraint).

Two near-misses worth recording so nobody re-runs them. Claude Desktop holds 9 io_uring
fds on this machine continuously — checked before blaming it; they cost approximately
none of the byte budget, so it is a red herring. And an early "0 rings available" reading
was my own probe not yet reclaimed rather than a real shortage: the same 7–14 ms effect,
seen from the other side.

## Per-core clocks, re-measured

Both arms unprivileged, 300 000 requests completed each. The direction **reversed** from
the hardened-kernel run, and the idle column is the real result:

```
            pkg mean   cores >3GHz   cores <1.5GHz
idle   epoll    2283         8.00          8.00
idle   uring    3053        11.70          4.30     offset +770 MHz (+33.7%)
load   epoll    3347        13.81          2.19
load   uring    3458        14.63          1.15     offset +111 MHz (+3.3%)
```

At idle, with **zero clients connected**, epoll parks 8 cores at the 1103 MHz floor and
io_uring parks 4.3 — four cores that never park, exactly the worker count. That is
`src/net/io_uring/uring_context.cpp:492`'s 1 µs timeout, visible with no load at all, and
it is a cleaner statement of the mechanism than any loaded measurement.

**Withdrawn:** my earlier "io_uring sits 147 MHz *below* epoll" from the hardened host is
the opposite sign to this. That run had io_uring as root and epoll unprivileged, so the
scheduling class differed between arms and the figure isolates nothing. It should be
dropped rather than reconciled. The idle result above has both arms as the same
unprivileged user and carries no such caveat.
