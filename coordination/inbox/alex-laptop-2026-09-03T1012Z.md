# QUIC path migration verified on the wire — and the committed test passes on the broken code

## The result

`verify_http3_migration.sh` passes on `quic/cid-routing-reconciled` (`cb403edbb`), first
attempt: 4 UDP sockets across 4 workers, `client_ok=1`, `forwarded_out=4`,
`forwarded_in=4`, `accepted=1`, `stateless_resets=0`. A QUIC connection survived its
client changing address and userspace CID forwarding fired.

## Verified on the wire, not from the script's own report

tcpdump is not installed and installing it is a system change, so a small AF_PACKET
sniffer was run inside the server namespace instead.

- **The client genuinely changed address.** Same connection, source `…:44865` during the
  handshake (t=0.000–0.005), then `…:40117` at t=2.004.
- **The response came over the same connection, not a fresh one.** No long-header packet
  after t=0.005 — so no new Initial — and `accepted=1` server-side.
- **The connection identifier did NOT change.** Byte-identical destination CID
  `02df10d2b426aec6583c235fab20eeb2` on both sides of the move.

## Why the third point matters

The fix concerns additional advertised connection IDs never becoming lookup keys, and
RFC 9000 requires a *migrating* client to switch to a fresh destination CID. SNAT
rebinding is invisible to the client: it never learns it moved, so it never switches CID,
so the original single map entry still resolves. **The committed test exercises the
SO_REUSEPORT hash-miss forwarding path and never reaches the defect that was fixed.**

## The experiment that settles it

The ngtcp2 client's `--change-local-addr` performs a real client-initiated migration with
path validation, which does require a fresh CID. Both tests were run against both trees,
holding the test constant and varying only the code under test (`b68257d40` is the parent
of the fix, `00f6546ce`):

| code | test | result | client_ok | stateless_resets | forwarded_out |
|---|---|---|---|---|---|
| pre-fix | SNAT (committed) | **PASS** | 1 | 0 | 4 |
| pre-fix | self-migration | **FAIL** | 0 | **3** | 3 |
| post-fix | SNAT (committed) | PASS | 1 | 0 | 4 |
| post-fix | self-migration | PASS | 1 | 0 | 7 |

The committed test passes on the broken code. The self-migration variant fails it with
exactly the documented symptom — three Stateless Resets tearing down a live connection —
and the pre-fix client log shows the server advertising `NEW_CONNECTION_ID` seq 1–5, none
of which was ever a lookup key.

On the fixed tree the wire shows the intended path: at t=2.004 the client moves to port
40984 **and** switches to DCID `02285ff7ed9f0a5a816fae70c0f1eff5`, a CID it had only been
advertised, with no new Initial, and the request completes.

This is the third green check today that does not check.

## Two smaller findings

**Every run leaks its server.** The cleanup trap kills `$SERVER_PID`, which is the
`ip netns exec` wrapper rather than the `http3_app_mig` grandchild, and the app installs
no SIGTERM handler. Seven four-worker servers were left behind across these runs and
required SIGKILL.

**The dependency script was not needed.** Its pins (`ngtcp2 v1.25.0`, `nghttp3 v1.18.0`)
are exactly what this host has, and the private OpenSSL 3.5.8 exists because
distributions lag — this one does not, at 3.6.4. Only ngtcp2's examples were built,
against the system libraries: minutes rather than an hour. **Deviation to record: OpenSSL
3.6.4 rather than the pinned 3.5.8.**

Namespaces and nftables rules used by the harness live inside throwaway network
namespaces and are torn down with them; the host firewall is untouched.
