# alex-laptop: the io_uring mechanism, the clock work, and the futex attribution

Consolidated, covering the reports sent as messages since the 0202Z file. Written as one
entry rather than five because the five are one line of work and the intermediate ones
are only legible in order. Each section says what was measured and what was refused.

## 1. The io_uring mechanism, read not changed

`src/net/io_uring/uring_context.cpp`:

    line 473   worker_loop:  while (!stopped_) { poll_and_resume(i); process_callbacks(i); }
    line 489   comment:      "Use short timeout - balance between latency and CPU usage"
    line 492   ts.tv_nsec = 1000;   // 1us timeout
    line 506   io_uring_wait_cqe_timeout(&ring, &cqe, &ts)

An unconditional loop with a one microsecond deadline. Each turn issues one
io_uring_enter, so with nothing to do the loop turns as fast as the syscall allows:
about 58 000 per worker per second, 230 000 across four, set by the cost of an enter
rather than by the workload. That is why syscalls-per-request is not a valid normaliser
for that backend, and why the same figure looked like 4.752 per request in the
feasibility probe, which I withdrew.

Correction to the code's own comment while reading it: line 145 says
io_uring_wait_cqe_timeout consumes an SQE for its timeout on kernels without
IORING_FEAT_EXT_ARG. This kernel has it, read from a live ring: features=0x3ffff. So no
timeout SQE is consumed here. The comment is not wrong in general; it does not describe
this host.

## 2. Per-core clocks: io_uring holds the package down

Both arms over the namespace pair, identical completed counts, all sixteen cores sampled
every 0.5 s.

    fastest core, io_uring minus epoll
      idle, server up, no load      -147 MHz
      3000 requests a second        -152 MHz
      10000 requests a second       -141 MHz

Flat across zero to ten thousand. A gap that does not move with load is not caused by
the load. Per-core medians at 3000 are mostly -180 to -216 with a median of -181; three
of sixteen came out positive and I have not chased them, which in a single thirty second
run with generator, sampler and four workers migrating is not structure.

This is a mediator, not a confounder: the treatment causes the clock change, so the
slower package is part of what io_uring costs and must be reported alongside the latency
rather than corrected out of it. Magnitude is hardware-specific; a part with no boost
headroom would show little of it.

A near miss worth recording. The first attempt produced completed=0 with 64 socket
errors on both arms, because the server was launched without `ip netns exec srv` and sat
in the wrong namespace while the generator looked for an address it could not reach. The
sampler produced sixteen columns of plausible megahertz for a server nobody talked to.
Caught by checking the generator's completed count before looking at the clocks; the
script now refuses samples from a run carrying under a thousand requests.

## 3. The clock reads, attributed and then reduced

Attribution by perf call graph, server pid only, 8000 connections:

    IdleTimeout::touch, 3 inlined sites   idle_timeout.hpp:127-129   4.00/conn   41%
    TimerQueue run loop                   timer_queue.hpp:107        3.68/conn   38%
    TimerQueue::schedule                  timer_queue.hpp:55         2.01/conn   21%

None needs nanosecond precision; all three are deadline arithmetic against a 30 000 ms
timeout. Nothing measurement-grade appears on the path at all.

Two measurements then decided what could be done about it:

  - `cv.wait_until` makes exactly one clock read per wait, the same whether the deadline
    is future or already past. So restructuring the loop to wait unconditionally would
    remove only the explicit read at :107, not wait_until's own.
  - `pthread_cond_clockwait` accepts CLOCK_MONOTONIC and CLOCK_REALTIME and rejects both
    coarse clocks with EINVAL. A deadline a condition variable will wait on cannot live
    in the cheap clock, so the TimerQueue's 5.69 per connection is not reachable by
    substitution at all. That is a constraint, not a trade.

So only `touch` could move, and it did. `now_ns()` rather than `touch()`, because both
the store and the subtraction come through it and changing one side would put a coarse
timestamp and a fine one across a subtraction.

    rate    clock_gettime/req            total syscalls/req
            before   after   delta       before   after   delta
    10000    2.002   0.001  -2.001        7.134   5.070  -2.064
      400    9.269   4.961  -4.308       30.385  24.441  -5.945

All four cells accepted, 184/184 tests pass, no latency regression. Coarse granularity
measured at 1.00 ms against a 30 000 ms decision, four orders of magnitude finer than
the quantity.

## 4. The futex attribution, and a remainder that does not move

The non-clock part of that delta was unexplained, and futex was not in the instrumented
set, so it could not be checked. Added permanently, then measured both sides again:

    tracepoint            before/conn   after/conn      delta
    accept4                     1.006        1.006     +0.000
    clock_gettime               9.204        4.952     -4.252
    close                       1.006        1.006     +0.000
    epoll_ctl                   6.026        6.026     +0.000
    epoll_wait                  3.083        2.692     -0.392
    futex                       5.763        4.691     -1.073
    recvfrom                    2.006        2.006     +0.000
    sendto                      1.000        1.000     +0.000
    -- named subtotal          29.096       23.380     -5.716
    -- UNNAMED remainder        1.065        1.065     -0.000
    == raw_syscalls total      30.161       24.445     -5.716

Named coverage 96.5%, against 77.0% before futex was counted. The non-clock delta of
1.464 is fully named: futex -1.073 and epoll_wait -0.392. Removing 4.25 kernel entries
per connection removed 4.25 preemption points, and the server contends and wakes less.

The strongest row is the remainder: 1.065 before, 1.065 after, delta -0.000. Every
syscall the change touched has a name. The residual is stable across the change and is
therefore not part of this story; chasing it would be curiosity spending machine time.

The five unchanged tracepoints are the second strongest. Identical accept4, close,
epoll_ctl, recvfrom and sendto to three decimals is what makes this a controlled
comparison rather than two numbers that moved.

## 5. Numbers withdrawn or corrected during this work

  - `io_uring_enter` at 4.752 per request: withdrawn. It was never per request; the
    enter rate is time-proportional and the load happened to be 20 000 a second.
  - The clock_gettime "fixed floor" of about 3038 a second: withdrawn. A two-point fit
    whose two points differed in shape as well as rate. A three-rate ladder at one shape
    gave 2.001 per request with a floor of ten a second, so there is no floor, and the
    churn reads are genuine per-connection work after all.
  - The churn-over-keep-alive syscall ratio has four defensible values: 4.264 raw,
    4.116 with the clock rows removed, 4.821 raw after the change, 3.843 after with the
    remaining clock rows removed. 4.116 is the one to quote for unchanged code on a
    healthy host, because there the reads never enter the count. Subtracting the row is
    not the same as removing the work: actually removing it took 1.464 other syscalls
    with it.
  - Do not pair the -4.252 from section 4 with the -4.308 from section 3. Different
    runs. Each table is internally consistent; halves of two are not.

## 6. Method notes worth keeping

  - A decomposition with k unknowns needs at least k+1 points. At exactly k the residual
    is zero by construction and the fit carries no information.
  - Two quantities that moved together are not evidence about either separately, so
    agreement between two sources processed through the same confound confirms only that
    the confound was the same.
  - An instrument that keeps producing well-formed output when the thing it measures did
    not happen is the dangerous kind. Four were caught this way, each by asserting on a
    different quantity: perf counting zero, the pid resolution finding nothing, the
    census readiness probe, and the per-core sampler running against a server nobody
    reached.
  - The staleness gate needs every binary to postdate its CMakeCache and every source.
    Touching a source to satisfy one binary moves the staleness to the other. Delete both
    binaries and rebuild both after the last source edit.
