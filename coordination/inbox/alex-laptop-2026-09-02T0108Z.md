## 2. Why the io_uring cells still fail, precisely

Both are the clock **rising**, not falling: 3878 -> 4059 and 3851 -> 3958. Every drift
rejection this host has produced since the first fix has been a rise. The rule takes
|end - start| / start, so it catches ramp-up and throttling alike, and what is left here
is ramp.

Two things about it are worth your judgement rather than mine:

  - The io_uring cells start lower than the epoll cells: 3878 and 3851 against 4042 and
    4067, sampled at the same point after the same 5 second warmup on the same host
    minutes apart. The io_uring server is polling io_uring_enter at ~230000 a second
    from the moment it starts, so the package is not idle during its warmup; it starts
    the measured window further from the ceiling and spends the window climbing.
  - Busier is not monotonically better here. io_uring keep-alive is the busiest cell of
    the four and has the largest residual drift at 4.7%, while io_uring churn at a
    twenty-fifth of the request rate has 2.8%.

I have not changed anything. Whether a rise inside the measured window should count
against a rule aimed at throttling is a methodology question, and a longer warmup is the
obvious cheap test; say the word and I will run one io_uring cell at 30 seconds warmup.

## 3. The clocksource, which is the important part

Answering "where do the clock reads come from" turned up something larger than the
question.

**This machine's clocksource is `hpet`, and `tsc` is not in the available list at all.**

    current_clocksource: hpet
    available_clocksource: hpet acpi_pm

The kernel disqualified the TSC at boot:

    [4.137460] clocksource: Watchdog remote CPU 4 read timed out
    [5.137381] clocksource: Marking clocksource tsc unstable due to frequency skew
    [5.137418] tsc: Marking TSC unstable due to clocksource watchdog

That is a known false positive pattern on some AMD parts. The consequence is not subtle.
With hpet the vDSO cannot serve `clock_gettime(CLOCK_MONOTONIC)`, so every call is a
real syscall and a memory-mapped HPET read. Measured here:

    clock_gettime(CLOCK_MONOTONIC)         1931.5 ns per call, 1 syscall per call
    clock_gettime(CLOCK_MONOTONIC_COARSE)     5.0 ns per call, 0 syscalls (vDSO)

A 200000-iteration loop produced exactly 200000 `sys_enter_clock_gettime` events. On a
host with a usable TSC the same loop produces **zero** syscalls and costs about 20 ns a
call.

### What that means for the record

  - Every `clock_gettime` in the syscall tables is an artifact of this host. On a
    TSC host that column is zero and the totals drop: epoll keep-alive from 7.09 to
    about 5.09 per request, epoll churn from 30.53 to about 21.2.
  - It is not only a count. `std::chrono::steady_clock::now()` costs about 1.9 us here
    against about 20 ns on a normal host, roughly a hundredfold. At the ~1.7 clock reads
    per request measured below that is about 3.3 us of pure clock overhead per request
    that belongs to this machine's firmware, not to the framework.
  - No gate catches it. Nothing in the environment record names the clocksource, so a
    campaign from this host and one from a TSC host would pool cleanly and differ by
    microseconds per request for a reason nothing in the record explains.

**Suggested, not done:** record `/sys/devices/system/clocksource/clocksource0/current_clocksource`
in the environment and add it to the fingerprint, and consider refusing a timing campaign
on a host whose clocksource is not tsc. That is a validity decision and a fingerprint
change, so it is yours. `tsc=nowatchdog` or `tsc=reliable` on the kernel command line is
the usual remedy for the false positive, but that is a boot parameter and Alex's call,
not mine; I have changed nothing.

## 4. Where the clock reads actually come from

They are mostly not per connection. Modelling count-per-second as `a * rate + b` from the
two rates, independently for each backend:

    epoll     20015/s @10000,  3717/s @400  ->  a = 1.698 /req,  b = 3038 /s
    io_uring  20018/s @10000,  3450/s @400  ->  a = 1.726 /req,  b = 2759 /s

The two backends agree on a per-request slope of about 1.70 and a fixed floor of about
2900 a second. They should agree: the clock code is shared, in the timer queue, the idle
timeout and the serve loop, and neither backend has any of its own. That agreement across
two independent measurements is the reason I believe the decomposition.

So the "9.293 clock reads per established connection" is **82% floor**: 7.60 of it is a
fixed ~3038 a second divided by a 400 a second request rate, and only about 1.70 is per
request. At 10000 a second the same floor is 0.30 of the 2.002. The per-request figure is
the same 1.70 in both shapes and both backends.

That is the same normalisation artifact as `io_uring_enter`, smaller and mixed rather
than pure: a fixed-rate loop divided by a request count. `timer_queue.hpp:107` reads the
clock once per iteration of the timer thread's wait loop, which is a fixed-rate reader,
and it is the obvious candidate for the floor.

So the deadline machinery is **not** arming nine times per connection. It reads the clock
about 1.7 times per request and something reads it about 2900 times a second regardless.
Worth fixing anyway on this host, where each of those reads is 1.9 us, but it is not the
per-connection cost it looked like.

Two-point fits with two unknowns have no residual to check. A third rate would test
linearity and I can run one on request.
