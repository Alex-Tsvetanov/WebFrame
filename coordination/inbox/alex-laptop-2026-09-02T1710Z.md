## The wake defect, which turned out to be three defects

Reported at 15:10Z: io_uring's `wake()` wrote to an eventfd nothing read. The prescribed
fix, a no-op submitted under the submission lock, measured at a median delivery of 962us
against a 1ms timeout — inert, because the worker holds that lock for the whole duration
of its wait, so the no-op could not be submitted until the wait it was meant to interrupt
had already ended.

**That generalises, and it is the useful part:** any wake that has to reach the ring
through the submission queue must take the lock the parked worker is holding, so it can
never arrive earlier than the timeout it is trying to pre-empt. A wake has to touch no
submission entry at all.

The working shape: a single-shot poll armed on an eventfd at ring init, and `wake()` as a
plain 8-byte write. No submission entry, no lock, correct whatever the worker is doing.
The completion carries a sentinel distinct from null, because it is acted on rather than
skipped and a genuine lost user_data must not be mistaken for it; the counter is cleared
with an ordinary read and the poll re-armed after the drain, so the lock is never held
across the inline coroutine resumes.

epoll had the same defect and worse: `post()` pushed onto a queue and did nothing else, so
a parked worker ignored it until its 100ms timeout expired. Measured at 50ms delivery. The
timer queue routes every idle timeout and handshake deadline through `post()`.

kqueue was found to have it too, on the machine that can build it, by the test written
here. Delivery there measured 98.5ms against a 100ms timeout.

Median delivery of a posted callback on an idle two-worker context:

| backend | before | after |
|---|---|---|
| epoll | 50138 us | 41-55 us |
| io_uring | 962 us | 9 us |

**The result is not the three fixes.** Three of four backends silently delayed posted
work, timers and shutdown by the length of their own wait, on three operating systems, and
every one passed a suite that never measured delivery latency on an idle loop. The suite
could not have caught it because nothing asked. One test, written for one backend, found
it on all three. The one backend that was correct is the one whose platform provides a
wake primitive that cannot be forgotten; the three that were wrong all needed a separate
mechanism remembered and wired up. That is a finding about what test suites cannot see,
not three unrelated bugs.

The test measures a median over 21 posts rather than one, because on a machine whose cores
have gone idle the first wake costs several hundred microseconds of C-state exit by
itself, which is the same order as the timeout being detected. A single-post version
passed and failed at random, which is how the submission-lock problem nearly went
unnoticed.

## The wait lock

Where the kernel takes a wait's timeout as an argument rather than as an operation
occupying a submission entry — a feature bit present since 5.11 — the wait submits
nothing, is not a producer, and the lock protects nothing while blocking every other
submitter for the length of the timeout. The lock is now skipped where the bit is set.

This was checked against the library documentation rather than assumed, and the direction
turned out to be the opposite of what had been supposed: the implied submit is on **old**
kernels without the feature, not new ones with it. Without the bit the wait really is a
producer, the lock is required, and an untimed wait would be unsafe for off-worker
submission — that last point is a deadlock rather than a delay, since the lock would be
held until something completes while the submitter that would complete it is blocked on
the mutex. Recorded in the code, because the visible version is the one that skips the
lock.

## Test-suite budget: two mechanisms, not one

Adding a fifth io_uring context to the suite put the per-user ring budget over again. It
took two remedies and neither fixes the other, which is why this looked settled twice:

- **Asynchronous release**, 7-14ms after a process exits, makes consecutive tests overlap
  in accounting though never in time. Not concurrency; a lock does nothing. The bounded
  retry handles it — with the retry alone, `-j1` passes 5 of 5.
- **Simultaneous demand.** Two tests each retrying hold what they have already taken while
  waiting for the rest, so they starve each other. No retry resolves that — with the retry
  alone, `-j16` failed 3 of 5.

With both: 186 of 186 over five consecutive runs. An earlier report here said the resource
lock was the wrong instrument; that was right about sufficiency and wrong about necessity,
and the evidence at the time could not have distinguished, because the suite then had one
fewer io_uring context.

## Schema 7 and 8

**7, `server_euid`.** Version 6 measured who ran the load but nothing measured who ran the
server, so the arrangement's central claim rested on a free-text label. That became
load-bearing once root turned out to be exempt from the limit ring memory is charged
against. The driver refuses a run whose two euids differ unless the cell declares why.

**8, the interface the run actually used.** The arrangement was asserted by a route metric
and nothing else: where a host has more than one interface on a subnet, which carries a
run is decided by a number that can change at a lease renewal, and a run that moved medium
would still produce a plausible figure. The generator now reads it from its own socket
after the connection is established, keeping the interface name and the link's speed,
duplex and MTU, and discarding the address. Recorded per run rather than per campaign,
because the failure is a medium changing partway through and a campaign-level field cannot
express that event at all. A run over an unexpected interface is refused; absent rather
than refused off Linux.

## Shared socket options

The four backends configured accepted sockets differently, so every cross-arm number was
partly a comparison of socket options. One helper now applies one policy from each
backend's connection constructor. Its own effect on latency measured as nil at the low
rates tested, which is the honest thing to say: the confound was real and had to go, and
it was not measurably biasing those cells.

## The link investigation

Conclusions only, per the rule at the top.

The two machines are on the same segment with no router hop between them, confirmed at
layer 2. The other machine does not answer ICMP echo — a firewall default, not an absent
host — so the round-trip baseline will instead be a TCP handshake, which has the better
justification anyway: it exercises the stack path a connection uses, where ICMP does not.
It waits for the other machine's campaign to finish.

**The idle-state finding survives into network measurement.** On a path where the remote
end and the wire were identical and only the local receiving cores' idle state changed,
the median round trip moved by 220us. The minimum barely moved, which says the floor is
the wire and the wake-up sits on top of it. Any two-host latency comparison that does not
control for the receiving core's idle state is measuring the idle governor as well as the
network, and the error is hundreds of microseconds.

**A conclusion withdrawn.** I wrote that a per-packet spread of a few hundred microseconds
means the path cannot resolve a 60-85us difference. That does not follow: the comparison
is between per-run medians, whose standard error falls as the square root of the sample
count, so at around a hundred thousand requests a run the per-packet spread is not the
binding quantity. What decides resolution is the run-to-run spread of per-run medians,
which the existing machinery already reports and which does not yet exist for the wire.
The open questions are whether network noise is autocorrelated enough to collapse the
effective sample count, and whether any variation is correlated with the arm rather than
added independently. Both are empirical. Neither machine should write a sentence about
which medium was correct for the demultiplexing claim until that number exists.
