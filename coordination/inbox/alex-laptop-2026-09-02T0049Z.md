## A. The network namespace pair

`benchmark/netns.py`, a module with a `__main__`: `up`, `down`, `status`.

Working, verified by lifecycle and by traffic:

    down on an absent pair    -> "pair already down", rc=0
    up                        -> srv=10.77.0.1 gen=10.77.0.2, rc=0
    up again                  -> "pair already up", rc=0
    ping gen -> srv           -> 2/2, rtt 0.045 ms
    up --profile wan50        -> netem 8001: limit 100000 delay 25ms, both ends
    ping under wan50          -> rtt 50.153 ms, i.e. 25 ms per direction as intended
    up --profile none         -> qdisc noqueue, i.e. no netem at all

`none` installs no qdisc rather than a zero-delay netem, because netem enqueues,
dequeues and accounts even when it delays nothing and a control arm carrying that cost
is not a control. The netem limit is explicit at 100000 packets: the default 1000 is
about the number in flight at 20000 rps over a 50 ms round trip, so the default is
exactly where silent drops begin.

### The server needed a launcher, and three things assumed Popen's pid was the server

`--generator-command` already existed. Without a counterpart the server stayed on the
host and the arrangement was one-ended, so `CorouteServer` takes a `launch_prefix` and
`run_campaign` takes `--server-command`, refused without `--generator-command`.

The server's prefix deliberately does NOT drop back to the invoking user the way the
generator's does. io_uring needs CAP_SYS_ADMIN here, so an io_uring cell has to stay
root, and if only that arm were root the epoll arm would differ in scheduling class as
well as in backend. Both arms run the same way. The generator does drop: verified, the
`runuser -u` prefix means it is not root.

Three things broke on a prefix, all silently, all fixed:

  - resource cost was read from sudo, which spends microseconds asleep in wait()
  - terminate() reached sudo, which does not pass signals to a process launched through
    `ip netns exec`, so the server outlived the run holding its port
  - the held-port gate probed this host's port rather than the namespace's, where it
    would have succeeded against exactly the stale server it exists to catch

and a fourth found only by running it: `wait_until_ready` connected to 127.0.0.1, which
with a prefix is the wrong namespace. Every run was filed as a 30 second readiness
timeout however healthy the server was. That is commit 68f4a8a48.

The server pid is found by walking children and comparing the first argv entry, not
`/proc/PID/comm`: TASK_COMM_LEN truncates comm to fifteen characters and
"benchmark_server" is sixteen, so an exact match never fires.

## B. The syscall counter

`--count-syscalls` on `run_campaign`. Working end to end over the namespace pair:

    whole_run=100000  raw_syscalls:sys_enter=709454  ->  7.095 syscalls/request
      accept4              64   0.001/req
      clock_gettime    200394   2.004/req
      close                64   0.001/req
      epoll_ctl        200299   2.003/req
      epoll_wait       108009   1.080/req
      recvfrom         100107   1.001/req
      sendto           100000   1.000/req
    second run: 711856 total, 7.119/req, same shape

    syscall_counter: "perf stat -e 12 tracepoints, -p server,
                      privilege=root via PATH wrapper (/usr/local/bin/perf)"

Adding clock_gettime and epoll_ctl was worth more than expected. The named tracepoints
now account for 708937 of 709454, which is **99.93%**, against 38.5% in the feasibility
probe. The breakdown is now a breakdown rather than a sample of one.

The window is the generator's lifetime exactly, bracketed by the driver around
`generator.run` rather than a fixed sleep, and the counts normalise by
`requests_total_whole_run`, so the warmup is inside both the numerator and the
denominator. Schema is at version 5 with `syscall_counts` and `syscall_counter`, absent
rather than empty at version 4 and below.

### Four ways it failed first, all of which produced a confident zero

The non-zero assertion earned its place immediately; every one of these was caught by it
rather than written to a table.

1. `tempfile` was not imported. Recorded as a failed run, not as zero syscalls.
2. `exec perf` execs the PATH name, and the perf on PATH here is a wrapper that adds
   sudo, so the pid the shell recorded was sudo's. SIGINT went to sudo, perf was never
   told to stop, and perf writes its counts on SIGINT and nothing otherwise.
3. The counter reported the host as allowing unprivileged counting. It does not.
   `/usr/local/bin/perf` is two lines: `exec /usr/bin/sudo -n "/usr/bin/perf" "$@"`.
   The probe succeeded, `id -u` inside it printed 0, and the record would have said
   "unprivileged" about counts taken as root. `/usr/bin/perf` invoked directly still
   fails with "can't access trace events", because tracefs is mode 0700 and perf reads
   the tracepoint id out of tracefs before it ever calls perf_event_open; the
   cap_perfmon and cap_sys_admin file capabilities the binary carries do not help with
   that. The same wrapper pattern covers ip, sysctl, bpftool, bpftrace, cpupower and
   pacman on this rig.
4. `fs.protected_regular = 1` on this hardened kernel. The counter created its output
   and pid files with mkstemp, as this user, and root then could not write them: the
   rule forbids writing an existing file owned by someone else in a sticky
   world-writable directory, and /tmp is exactly that. perf said "failed to create
   output file: Permission denied", wrote nothing, and the total came back zero. A
   private mkdtemp directory is 0700 and neither sticky nor world-writable, so the rule
   does not apply inside it.

Number 4 was only diagnosable because I made the assertion print perf's own stderr,
which had been piped and never read. That is the same mistake the server's startup
failures used to make, and it is worth stating as a rule: anything this harness pipes,
it must read on the failure path.

## What is NOT delivered, and why I think it is yours rather than mine

**No accepted records.** Every run on this machine is rejected by the CPU frequency
drift gate. Observed, across four campaigns: 6.0%, 6.9%, 2.9%, 10.3%, 7.8%, 3.4%, 6.2%,
4.1%, 6.8%, against a 2% limit. The runs themselves are clean: the offered rate is
achieved, errors are zero, latency is stable.

I do not think this is only "laptops throttle". The gate samples `cpu_mhz_start` at
driver.py:227, which is BEFORE `server.start()` at 236 and before `generator.run` at 261,
and `cpu_mhz_end` at 310. The warmup is therefore inside the drift window. Warmup exists
to let the machine reach steady state before anything is measured, and as sampled it
counts the settling against the gate instead. Raising `--warmup` from 2 to 25 seconds
did not help and one cell got worse, which is what that arrangement predicts: a longer
warmup means a longer decay before the "start" figure is ever compared to anything.

My reading is that `cpu_mhz_start` wants to be sampled at the start of the measured
window rather than before the server exists. I have NOT changed it: where the gate
samples is a methodology decision and it is on your side of the line, not mine. If you
want it moved, say so and it is a two line change. Until then this machine produces
rejected records only, which means the four-cell controlled comparison over the pair,
the part of B that would be the mechanism section, cannot be taken here yet. That is the
one piece of brief 4 I have not done, and I would rather say so than hand you numbers
from a rig whose own gate refuses them.

**Also not done:** the bpftrace comparison. perf with an explicit list now accounts for
99.93% of the total, so the maintained-list objection has mostly evaporated, and I would
rather leave the instrument that is working and understood than swap it late. Say if you
want it evaluated anyway.

## One defect in the merged harness, not mine

`python3 -m benchmark.harness.selfcheck` FAILS on phase0-foundation at d32d6aab2, before
any of my commits, at "linux without systemd falls back to DMI". Verified in a clean
worktree of origin/phase0-foundation.

The cause is a sentinel collision in the test rather than a bug in the function.
`_virtualisation_linux(None, "QEMU Standard PC")` passes None meaning "no
systemd-detect-virt", but the function reads None as "go and ask the real system", finds
systemd-detect-virt present, gets "none", and returns None without ever reaching the DMI
fallback the case is about. It therefore passes on a host without systemd, which is
macOS, and fails on essentially every Linux host, which is why your macOS run of 227
checks was green. The production path is fine; the test cannot express what it is trying
to say. It needs a distinct sentinel or a patched `_run`.

I have not fixed it, to avoid a conflicting edit on a file your side may already be
touching. It is a test-portability defect, not a correctness one, so nothing measured is
affected.
