## Socket options: one shared policy

`configure_accepted_socket()` in `src/net/socket_options.cpp`, io_uring's option set as
ruled (TCP_NODELAY, TCP_QUICKACK where the platform has it, SO_SNDBUF 256 KB), called
from all four connection constructors. `set_tcp_opts` deleted. Platform obligations
(SO_NOSIGPIPE on kqueue, SO_UPDATE_ACCEPT_CONTEXT on IOCP) left where they were, being
obligations rather than policy.

Four connection types, not five: `TlsConnection` and `PrefaceConnection` wrap an existing
`Connection` rather than owning an accepted descriptor, so they inherit the policy from
the socket underneath and must not apply it themselves.

Verified under strace that both Linux backends now set all three on the accepted socket,
rather than inferring it from the code.

**The policy's own effect on epoll latency is nil**, which is the honest thing to put in
the method section:

The confound was real and had to be removed, but it was not measurably biasing these

a property of the control, not of the policy.

**TLS was never confounded.** `App::run` has one accept path and TLS wraps an
already-accepted connection (`app.cpp:62`); every filed campaign banner reads

reached the unit tests and the demux suites, not the campaign. So "what TLS costs" does
not need re-stating.

**The keep-alive syscall finding stands.** Those cells were keep-alive, 64 connections for

request against the 2.725 figure. Note that `setsockopt` is not in `SYSCALL_TRACEPOINTS`
and has always lived in the unnamed remainder of `raw_syscalls:sys_enter`. The churn cells
are a different matter, since there every request is a connection; they re-run cross-arm

## Review HIGH 1: the prescribed fix does not work, and neither backend had a working wake

The brief was: io_uring's `wake()` writes an eventfd nothing reads, fix it with an
`IORING_OP_NOP` submitted under `sq_mutex`, and add a test that posted work is delivered
well under the timeout.

I implemented exactly that. **The test failed**, and finding out why is the result.

### Why the NOP alone was inert

The worker holds `sq_mutex` **across** `io_uring_wait_cqe_timeout`. So `wake()` blocked
acquiring that mutex until the wait had already ended on its own timeout, and the no-op
was submitted after the delay it exists to prevent. Measured, 21 posts on an idle
two-worker context:

```
io_uring, NOP under sq_mutex:  median 962us, worst 996us   (1ms timeout)
```

Ineffective in precisely the way the eventfd was. The review's MEDIUM item on
`uring_context.cpp:524-527` describes this same object as something to document; it is not
documentable, it makes HIGH 1's fix a no-op.

### The fix that works

The lock exists because the wait takes an SQE for its timeout on kernels without
`IORING_FEAT_EXT_ARG`. Where that feature is present (since 5.11) the timeout is an
argument to `io_uring_enter`, the wait produces nothing into the submission queue, and the
lock buys nothing while costing everything: it blocks every other producer for the whole
duration of a blocking wait, and `wake()` is one of those producers. The feature is now
recorded at ring init and the lock skipped where it is present; without it, the old
behaviour and its limitation remain.

### epoll had the same defect, worse, and it was not in the review

`post()` pushed onto a queue and did nothing else, so a worker parked in `epoll_wait`
ignored it until the 100 ms timeout expired — **measured at 50 ms delivery** on an idle
context. `TimerQueue` routes every idle timeout and handshake deadline through `post()`.

Fixed with an eventfd registered edge-triggered in the epoll set with null `data.ptr`,
which the existing `if (!op)` branch already skips; drained on wake; written by `post()`
and by `stop()`. The destructor closes it after the workers are joined, because a worker
sitting in `epoll_wait` on a closed set is a use-after-close.

### Result

Median delivery of a posted callback on an idle two-worker context:

| backend | before | after |
|---|---|---|
| epoll | 50138 us | **41 us** |
| io_uring | 962 us | **5 us** |

186 of 186 on three consecutive runs (184 plus the new test's two arms).

The test takes a median over 21 posts rather than measuring one, because on a machine
whose cores have gone idle the first wake costs several hundred microseconds of C-state
exit by itself — the effect measured separately at ~490 us — which is the same order as
the io_uring timeout the test has to detect. The first post pays it and the rest do not,
so the median isolates the ring's wake latency from the CPU's. A single-post version of
this test passed and failed at random, which is how the sq_mutex problem nearly went
unnoticed.

Both comments claiming a completion wakes the wait regardless are corrected: true of
CQEs, false of posted work until now. One of those comments was mine, written in the
wait-timeout commit.

## Consequence for the blocking-wait experiment

It should not start before this lands. A wait that blocks indefinitely while holding
`sq_mutex` would not delay `wake()`, it would deadlock it: posted work, timer callbacks
and `stop()` would never be delivered at all. The `EXT_ARG` change is what makes that
experiment possible rather than merely tidier.
