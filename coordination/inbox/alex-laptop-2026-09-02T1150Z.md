## B resolved: the fix is a bounded wait, not a lock

The 10:30Z report established that `RESOURCE_LOCK` could not work, because the failure
survives at `-j1`. Coordinator ruled for a test-side wait rather than a retry inside ring
init, on the grounds that ring init is the code under measurement. Implemented on branch
`linux/uring-test-memlock-settle`:

- `tests/io_backend_arms.hpp` retries context creation, bounded at 250 ms in 5 ms steps,
  rethrowing the last error so a genuine defect still fails. The coordinator's brief
  described probing for a ring and waiting; retrying the creation itself was used instead,
  because a probe consumes budget whose release is equally asynchronous, and because
  `io_backend_probe()` already creates and destroys a ring immediately beforehand, so its
  own residue is part of what has to be waited out.
- The two demux scripts get the same bounded wait, since they launch real servers.

Serial runs went from 2 of 7 failing on every run to 0. **184 of 184 on five consecutive
runs at -j16**, as asked.

Two things fell out of this that were not in the brief.

**A flake of my own making.** The full parallel suite still dropped one test, and it was
not io_uring: "Activity resets the idle clock". IdleTimeout moved to
`CLOCK_MONOTONIC_COARSE`, which advances once per tick, measured at 1.00 ms here. That
case turns on the near-zero gap between a read and the timer looking, which under that
clock reads as either zero or a full tick; against its 1 ms timeout it is a coin flip.
Measured at 2 failures in 200 runs, and 0 in 200 with the coarse clock disabled, so the
cause is not in doubt. Its timeout and sleep moved to 20 ms and 50 ms, clear of the tick,
and the header now records the resolution floor the optimisation imposes rather than only
the precision it gives up. This is a defect I introduced when landing the coarse clock and
it would have sat in the suite as an occasional unexplained red.

**A latent bug in protocol_demux.py**, found while restructuring its launch: the retry
loop I first wrote collapsed the never-listened case into the listening one, so a launch
timeout would have read as success. Fixed before it went anywhere, but it is the same
class of error as the one the harness exists to prevent.

## Schema 7

Branch `linux/schema7-server-euid`. `server_euid` added beside `generator_euid`, read from
`/proc/PID/status` rather than inferred from the launch prefix, for the same reason the
generator is asked rather than assumed. The third field of `Uid:` is used, because the
effective uid is what the kernel checks for the RLIMIT_MEMLOCK exemption and the real uid
can differ from it under `runuser`.

The driver now refuses a run whose two euids differ, unless the cell sets
`privilege_asymmetry`. Declared asymmetry stays legal because it is sometimes the point: a
hardened kernel with `kernel.io_uring_disabled=1` gives io_uring to CAP_SYS_ADMIN only,
and measuring it there means a root server on purpose.

This reverses what the driver's own comment asserted, and the comment was corrected rather
than left to contradict the check beside it. The old arrangement, root server and
unprivileged generator, was correct for the hardened kernel this rig used to run; it would
now be the confound rather than the way round one.

Seven new self-checks. Confirmed non-vacuous by removing the refusal and watching them
fail. 301 checks pass.

## F — the wait timeout at `uring_context.cpp:492`, 1 us against 1 ms

One line. Both binaries built from the same tree differing only in that constant, both
arms measured identically, an epoll column carried through as a reference.

### The saving

```
                          io_uring_enter/s   per request   all syscalls/req
  before (1us)                     420 598        44.864             45.020
  after  (1ms)                      25 548         2.725              2.733
  epoll (reference)                      0         0.000              5.090
```

Four workers times a thousand wakeups a second is 4 000 of the 25 548, so the remainder is
proportional to the work rather than to the clock. That is the whole point: **syscalls per
request is a usable normaliser for this backend again**. The backend that appeared to cost
nine times what epoll costs in fact costs about half.

Full table per request, 10 000 rps keep-alive:

```
  tracepoint          1us (before)   1ms (after)   epoll (ref)
  io_uring_enter            44.864         2.725         0.000
  epoll_ctl                  0.000         0.000         2.001
  epoll_wait                 0.000         0.000         1.030
  recvfrom                   0.000         0.000         1.000
  sendto                     0.000         0.000         1.000
  futex                      0.155         0.007         0.057
  clock_gettime              0.000         0.000         0.000
```

Throughput was 9999.9 rps in all three arms with 300 000 completions each, so nothing was
bought by dropping work.

### The cost, which is real

At rates whose inter-request gaps exceed the timeout, so that it actually engages:

```
  offered 100/s over 4 conns    min   p50   p90   p99   p999
  before (1us)                   20    44    60    86    123
  after  (1ms)                   22    38    59    90    506

  offered 500/s over 8 conns    min   p50   p90   p99   p999
  before (1us)                   16    28    36    47     84
  after  (1ms)                   21    31    39    51     67
```

p999 at 100/s rose from 123 us to 506 us. That is about half the new timeout, which is
where a request arriving just after a wait begins would land, so the tail behaves as
theory says it should. p50, p90 and p99 moved by a few microseconds and not consistently
in either direction; at 500/s the tail improved. This is not a latency knob, because a
completion wakes the wait immediately whatever the value is.

### What it does not buy, which is the part worth stating

Idle, nothing connected at all:

```
                     pkg MHz   cores >3GHz   cores parked <1.5GHz
  before (1us)        3057.7         11.55                   4.45
  after  (1ms)        2739.9         11.08                   4.83
  epoll (reference)   2080.9          6.50                   9.50
```

The parking count moved by 0.38 of a core against a gap to epoll of 5.05. A thousand
wakeups a second per worker is still far too many to let a core reach the deep states, so
**the power and thermal cost of the completion model survives this change almost intact.
Only the syscall count went away.** Reporting the 16-fold saving without this would
misdescribe the change in exactly the direction we spent the night correcting.

### An unexplained observation, flagged not chased

The epoll reference shows a median latency of ~500 us at 500/s and ~490 us at 100/s,
against 28 us and 44 us for io_uring, with p90 770, p99 937, p999 1002 — a hard ceiling
near 1000 us and a distribution that looks uniform over 0 to 1 ms. epoll's own
`epoll_wait` timeout is 100 ms, not 1 ms, so that is not the source, and the arming
comment nearby describes an unrelated race. It reproduces across both rates. It is
outside F's brief and does not affect the before/after comparison, since both io_uring
arms share the same generator and namespaces, but it looks like a real ~1 ms structure in
the epoll path at low load and is worth its own investigation.
